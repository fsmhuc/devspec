# 测试策略 — TDD 驱动

> 所有功能开发和 Bug 修复必须遵循测试驱动开发（TDD）流程。测试不是事后补充，而是设计工具。

---

## 核心理念

**测试先行（Test First）** — 先写测试，再写实现。测试既是需求的精确表达，也是设计的验证工具。

---

## TDD 三步循环

```
┌──────────────────────────────────────────────────┐
│                TDD 循环                           │
│                                                  │
│   ┌──────────┐   ┌──────────┐   ┌──────────┐   │
│   │ 1. Red    │──>│ 2. Green  │──>│ 3.Refactor│   │
│   │ 写失败测试 │   │ 最小实现  │   │ 优化结构  │   │
│   └──────────┘   └──────────┘   └──────────┘   │
│        ▲                              │          │
│        └──────────────────────────────┘          │
└──────────────────────────────────────────────────┘
```

### 步骤 1: Red — 写一个失败的测试

- 根据规格中的验收标准和接口定义编写测试
- 测试必须能运行且**失败**（证明功能尚未实现）
- 测试应聚焦于一个行为，不要一次写太多

### 步骤 2: Green — 用最小代码让测试通过

- 只写让测试通过所需的最少代码
- 不要提前优化，不要"顺便"实现额外功能
- 测试通过即停止

### 步骤 3: Refactor — 在绿灯保护下优化

- 重构实现代码和测试代码
- 每次重构后运行测试，确保仍然通过
- 消除重复，改善命名，提取抽象

## 测试分层

| 层级 | 目的 | 范围 | 运行速度 | 必要性 |
|------|------|------|----------|--------|
| **单元测试** | 验证单个函数/类的行为 | 单个模块 | 毫秒级 | **必须** |
| **集成测试** | 验证模块间协作 | 多个模块 | 秒级 | 按需 |
| **E2E 测试** | 验证完整用户流程 | 整个系统 | 分钟级 | 关键路径必须 |

### 最低要求

- **每个功能**：必须有单元测试覆盖所有验收标准
- **每个 Bug 修复**：必须有回归测试重现原 Bug
- **每个 API 端点**：必须有接口级测试

---

## 测试先行规则

### 必须先写测试的场景

| 场景 | 测试要求 |
|------|----------|
| 新功能开发 | 先写单元测试，覆盖验收标准中的每一条 |
| Bug 修复 | 先写复现 Bug 的测试（Red），再修复（Green） |
| API 变更 | 先写/更新接口测试 |
| 重构 | 确保已有测试覆盖后再重构 |

### 豁免场景（不需要测试）

| 场景 | 原因 |
|------|------|
| 纯文档/注释修改 | 不影响运行时行为 |
| 纯规格文件修改 | 规格由 `validate` 工具检查 |
| 配置格式调整（缩进、排序） | 不影响逻辑 |

> 使用豁免时，必须在 commit message 中注明 `[no-test]` 并说明原因。

## 测试质量标准

### 好的测试

- **独立** — 不依赖其他测试的执行顺序或状态
- **可重复** — 每次运行结果一致
- **自描述** — 测试名称清晰表达被测行为
- **快速** — 单元测试应在毫秒内完成
- **聚焦** — 每个测试只验证一个行为

### 测试命名规范

```
test_<被测行为>_<场景>_<预期结果>

示例:
test_login_with_valid_credentials_returns_token
test_login_with_expired_password_returns_401
test_create_feature_with_duplicate_name_raises_error
```

### 禁止事项

- ❌ 删除失败的测试来"通过" CI
- ❌ 写只验证实现细节而非行为的测试
- ❌ 空的测试函数（`pass` / `return`）
- ❌ 跳过失败测试而不修复（`@skip` 需附理由和 Issue 编号）
- ❌ 测试中使用 `sleep` 或固定延迟
- ❌ 测试间共享可变状态

## 与开发循环的集成

### AI 开发循环中的测试

```
验证 → 生成 → 测试 → 分析
                ▲
                │
          测试失败 = 循环失败
          不允许静默跳过
```

- 测试阶段是**阻断性**的 — 测试失败时循环停止，必须先修复
- `--skip-tests` 仅在纯规格变更（无代码变更）时允许使用
- 找不到测试运行器时发出**警告**（不再静默通过）

### CI/CD 中的测试

- 测试必须作为 CI 流水线的一部分运行
- 测试失败阻断 PR 合并
- 覆盖率报告作为 artifact 保存

## 与规格的对应关系

```
spec/features/<feature>/spec.md
    │
    ├── 验收标准 ──────> 单元测试用例
    ├── 接口定义 ──────> API 测试用例
    ├── 边界情况 ──────> 边界测试用例
    └── 约束条件 ──────> 性能/安全测试

spec/features/<feature>/tasks.md
    │
    └── 写测试任务必须在实现任务之前（P0）
```

## 工作流集成

### 规格工作流中的位置

```
1. 理解愿景
2. 检查架构
3. 写功能规格
4. 拆分任务
5. 记录决策
6. 写测试（TDD: Red）     ← 新增
7. 实现代码（TDD: Green）
8. 重构（TDD: Refactor）
9. 验证审查
```

### Patch 工作流中的要求

```
1. 创建 Patch 文件
2. 记录问题和修复方案
3. 写回归测试（重现 Bug）  ← 强制
4. 实施修复
5. 运行测试 + 验证
6. 提交
```
