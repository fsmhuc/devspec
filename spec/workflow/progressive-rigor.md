# 渐进式严格度

> 不是所有变更都需要完整规格。简单变更用 Lite 模式降低文档负担，高风险变更用 Full 模式确保覆盖全面。

---

## 核心理念

DevSpec 默认提供完整的规格模板（目标、非目标、设计、接口、验收标准、约束、依赖、风险、边界情况、测试策略），但很多小功能不需要全部填写。

渐进式严格度将规格分为两个等级：

| 等级 | 适用场景         | 必填节数 | 说明                         |
| ---- | ---------------- | -------- | ---------------------------- |
| Lite | 大多数普通功能   | 3 节     | 轻量，快速推进               |
| Full | 高风险/跨模块    | 全部     | 完整覆盖，确保质量           |

---

## Lite 模式

### 必填节

1. **目标（Goals）** — 功能要解决什么问题
2. **设计（Design）** — 核心设计方案
3. **验收标准（Acceptance Criteria）** — 功能完成的判定条件

### 可选节

其余节（非目标、接口、约束、依赖、风险、边界情况、测试策略）可留空或省略。

### 适用条件

- 单模块内变更
- 不涉及 API/接口变更
- 不涉及安全
- 不涉及架构

---

## Full 模式

### 必填节

模板中的**所有节**都必须填写，包括：
- 目标、非目标、设计、接口、验收标准
- 约束、依赖、风险、边界情况
- 测试策略（含单元测试、集成测试、波及范围）

### 触发条件（满足任一即为 Full）

| 条件             | 原因                         |
| ---------------- | ---------------------------- |
| 跨模块变更       | 影响范围大，需要完整分析     |
| API/接口变更     | 影响外部调用方               |
| 安全相关变更     | 风险高，需要完整风险评估     |
| 架构影响         | 需要 ADR + 完整规格          |
| 数据模型变更     | 影响持久化层                 |
| 新增外部依赖     | 需要评估依赖风险             |

---

## 使用方式

### 在功能规格中声明

在 spec.md 头部添加严格等级：

```markdown
# 功能名称

> 状态: `draft` | `ready` | `in-progress` | `review` | `done`
> 严格等级: `lite` | `full`
```

### 创建功能时指定

```bash
# 默认 lite
python3 mcp/cli.py create-feature my-feature --goals "目标1"

# 指定 full
python3 mcp/cli.py create-feature my-feature --goals "目标1" --rigor full
```

### 验证时检查

```bash
# ds:verify 会根据严格等级调整检查项
python3 mcp/cli.py verify my-feature
```

Lite 模式下，`ds:verify` 只检查必填节和任务完成状态。
Full 模式下，`ds:verify` 检查所有节的完整性。

---

## 升级规则

Lite 模式可以在任何时候升级为 Full：
- 发现功能比预期复杂
- 新增了跨模块依赖
- 需要变更 API/接口
- 代码审查中发现风险

升级方法：将 `严格等级: lite` 改为 `严格等级: full`，然后补全缺失的节。

**降级不允许** — Full 模式一旦设定，不能降为 Lite。

---

## 与其他工作流的关系

| 工作流          | 影响                                       |
| --------------- | ------------------------------------------ |
| Delta Specs     | Delta 不受严格等级影响，始终使用完整格式   |
| ds:validate     | 不受影响（只做结构检查）                   |
| ds:verify       | 根据严格等级调整检查项                     |
| 测试策略        | Lite 仍需要测试（TDD 不可跳过），但测试策略节可省略 |
| ADR             | Full 模式的架构变更仍需 ADR                |

---

## 决策树

```
新功能:
├── 涉及架构变更？
│   └── 是 → Full + ADR
├── 涉及 API/接口变更？
│   └── 是 → Full
├── 跨模块？
│   └── 是 → Full
├── 涉及安全？
│   └── 是 → Full
└── 以上都否 → Lite
```
