# AI Agent 行为规范

> 所有 AI Agent 在本仓库工作时必须遵守以下规则。这些规则基于 Anthropic、OpenAI、Google 
> 等顶尖团队的 AI 开发最佳实践。

---

## 基本原则

### 原则 1 — 先读后写

**绝不在理解系统之前直接修改代码或规格。**

每次会话开始时：
1. 阅读 `spec/index.md`
2. 根据任务类型，按上下文加载策略加载相关文件
3. 确认理解后再行动

### 原则 2 — 规格驱动

**所有实现必须有对应的规格。**

- 没有规格 → 先写规格
- 规格冲突 → 先解决冲突
- 规格不完整 → 先补全规格

### 原则 3 — 最小变更

**每次变更应尽可能小且聚焦。**

- 一个 PR/commit 解决一个问题
- 避免"顺便"修改不相关的文件
- 大变更拆分为多个小步骤

### 原则 4 — 测试先行（TDD）

**先写测试，再写实现。测试是设计工具，不是事后补充。**

- 新功能 → 先根据验收标准写测试（Red），再实现（Green），再重构（Refactor）
- Bug 修复 → 先写复现 Bug 的回归测试，再修复
- 重构 → 确保已有测试覆盖后再动手
- 豁免场景：纯文档/纯规格变更（commit message 注明 `[no-test]`）

详见: `spec/workflow/testing-strategy.md`

## 操作规则

### 规则 1 — 永不覆盖规格

变更规格时使用 git 追踪变更，绝不直接覆盖无记录地重写。
- 重大变更前先创建 git 分支
- 废弃规格移至 `spec/archive/`
- commit message 清晰描述变更原因

### 规则 2 — 架构变更需要 ADR

任何影响 `spec/core/architecture.md` 的变更必须：
1. 先创建 ADR 文档（`spec/decisions/ADR-*.md`）
2. 列出备选方案
3. 获得人类确认后再实施

### 规则 3 — 功能不得与架构冲突

新功能设计前，检查 `spec/core/architecture.md` 中的架构约束。
如有冲突，先通过 ADR 修改架构。

### 规则 4 — 任务必须关联规格

`tasks.md` 中的每个任务必须能追溯到对应的 `spec.md`。
不允许无出处的临时任务。

### 规则 5 — 废弃规格归档

不再使用的规格：
1. 移至 `spec/archive/`
2. git commit 记录归档原因
3. 更新引用该规格的文件

### 规则 6 — 测试不可跳过

- 测试失败时，修复代码或测试，**绝不删除失败的测试**
- `@skip` 标记必须附带理由和 Issue 编号
- 开发循环中测试阶段是阻断性的 — 失败即停止
- CI 中测试失败阻断 PR 合并

## 审查门控（Review Gates）

### 可自主执行（无需人类确认）
- 读取和分析任何文件
- 运行验证和测试工具
- 创建 Patch（Bug 修复）
- 更新任务状态
- 补充文档和注释

### 需要人类确认
- 创建或修改功能规格
- 创建 ADR 文档
- 删除或归档任何文件
- 修改架构文档
- 任何涉及安全的变更

---

## 错误处理

当遇到问题时，按以下优先级处理：

1. **规格不完整** → 向人类提问，不要猜测
2. **规格冲突** → 列出冲突内容，请人类做决策
3. **实现不确定** → 提出 2-3 个方案，让人类选择
4. **工具失败** → 记录错误，尝试替代方案，仍失败则报告

**绝不在不确定时默默做假设。明确表达不确定性比假装知道更重要。**

## 输出格式规范

### 规格文档
- 使用 Markdown 格式
- 标题层级一致（`#` → `##` → `###`）
- 列表和表格对齐
- 决定用表格，列表用于简单枚举

### 代码变更
- 提供变更前后的对比说明
- 注释说明为什么这样改（不只是改了什么）
- 遵循项目现有的代码风格

### 沟通
- 先说结论，再说过程
- 不确定时说"我不确定，因为..."
- 需要信息时问具体问题，不要问开放式问题

## 多 Agent 协作协议

当多个 AI Agent 在同一项目工作时：

1. **领域隔离** — 每个 Agent 负责不同的 feature 目录
2. **冲突避免** — 修改共享文件前（如 architecture.md），先检查最新版本
3. **状态同步** — 通过 `tasks.md` 的状态更新传递进度
4. **依赖通知** — 完成阻塞任务后更新依赖任务的状态

## 思维框架

处理任何任务前，按以下步骤思考：

```
1. 理解 — 这个任务要解决什么问题？
2. 定位 — 需要哪些上下文？（加载对应文件）
3. 分析 — 现有设计如何？有什么约束？
4. 方案 — 有哪些可选方案？推荐哪个？为什么？
5. 测试 — 先写测试表达预期行为（TDD: Red）
6. 执行 — 用最小代码让测试通过（TDD: Green）
7. 重构 — 在绿灯保护下优化（TDD: Refactor）
8. 验证 — 运行验证工具和全量测试，确认无错误
```
